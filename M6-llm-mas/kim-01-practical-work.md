# КИМ-6.1. Лабораторная работа «Проектирование мультиагентной LLM-системы»

| Параметр | Значение |
|---|---|
| Модуль | 6. Мультиагентные системы на основе LLM |
| Тип КИМ | Лабораторная работа с устной защитой |
| Форма контроля | Текущий контроль (результаты используются в промежуточной аттестации) |
| Проверяемые индикаторы | LLM-4.1, LLM-4.3 (уровень Б) |
| Трудоёмкость | 6 а.ч. (ЛР) + подготовка в СРС 6 |
| Максимальный балл | 5 (см. [rubric-01.md](rubric-01.md)); минимум для зачёта — 3 |

## 1. Назначение и проверяемые результаты обучения

Лабораторная работа проверяет базовый уровень индикаторов **LLM-4.1** (построение мультиагентной LLM-системы, разделение ответственного и LLM-контуров) и **LLM-4.3** (реализация агентных паттернов взаимодействия). По итогам обучающийся:

- **знает** архитектуру мультиагентной LLM-системы (оркестратор, ролевая специализация, A2A, MCP), агентные паттерны (ReAct, Plan-and-Solve, «планировщик–исполнитель», «критик»);
- **умеет** настраивать взаимодействие оркестратора со специализированными агентами, подключать инструменты, задавать ограничения и проверять результат LLM-компонента;
- **владеет** навыком построения мультиагентной LLM-системы из готовых компонентов и разделения ответственного и LLM-контуров.

## 2. Условия выполнения

- **Среда и инструменты:** Python 3; локальная или облачная LLM с поддержкой вызова инструментов/функций либо детерминированный mock для contract tests; подключение инструментов по **MCP**; мультиагентный фреймворк по выбору (или собственная реализация оркестрации). Провайдер модели не регламентируется — оценивается архитектура и разделение контуров, а не конкретная модель. Mock подтверждает контракты и отказы, но не качество реальной LLM.
- **Форма работы:** индивидуально или в малой команде с разделением зон ответственности и индивидуальной защитой.
- **Артефакты ведутся в Git:** код, конфигурация, трассы взаимодействия (A2A/MCP), журнал вызовов инструментов, паспорт архитектурного решения, инструкция запуска.
- **Регламентированное использование ИИ-ассистентов** для разработки — при выполнении условий раздела 6 (отдельно от LLM-компонентов самой системы).

### Минимальный воспроизводимый старт

```bash
python examples/m6_guarded_orchestrator.py
python examples/m6_protocol_slice.py
python examples/m6_protocol_slice.py --unavailable-tool
```

Первый пример оставляет безопасный запрос в состоянии
`awaiting_human_decision` и блокирует опасный без внешнего эффекта. Второй
показывает `A2A 1.0.0` на границе агент↔агент и `MCP 2025-11-25` на границе
агент↔инструмент; позитивный путь завершается `completed`, отказ инструмента —
`failed` без артефакта. Это **семантический contract slice**, а не заявление
wire-conformance. Границы профиля:
[минимальный](../docs/resource-profiles.md#минимальный-профиль-квалифицирован).

## 3. Задание

1. **Постановка.** Задать прикладной сценарий (по варианту), где оркестратор получает запрос, а специализированные агенты формируют предложения; ответственный контур подтверждает значимое действие.
2. **Архитектура и границы протоколов.** Реализовать систему **«оркестратор + не менее двух специализированных агентов»**. A2A применяется только для делегирования задачи независимо управляемому агенту, MCP — только для доступа агента/модели к инструменту, ресурсу или контексту. Для учебного baseline закреплены A2A `1.0.0` и MCP `2025-11-25`; RC/draft не выдаются за обязательную стабильную версию.
3. **Проверяемый A2A slice.** До делегирования проверить Agent Card/capability и версию; различать `task_id`, состояния `submitted` / `working` / `input-required` / `completed` / `failed` / `canceled`, сообщения и результирующий артефакт; определить timeout, retry, idempotency и cancel.
4. **Проверяемый MCP slice.** Объявить capability инструмента/ресурса; проверить authorization по audience, scope, ресурсу, задаче и сроку; обработать запрет и недоступность инструмента. Исходный пользовательский credential не передаётся агентам как общий токен.
5. **Агентный паттерн (LLM-4.3).** Применить хотя бы один паттерн: ReAct/Plan-and-Solve внутри агента и/или «планировщик–исполнитель»/«критик» между агентами; обосновать выбор.
6. **Ответственный контур и валидация.** Реализовать проверку результатов LLM-компонента фиксированными правилами; значимое действие выполняется только после валидации/подтверждения. Для каждого класса действия указать полномочие, бюджет, stop/revoke и ответственную роль.
7. **Наблюдаемость.** Журналировать `task_id`, версии, policy decision, вызовы инструментов и моделей, обмен сообщениями/артефактами, ошибки, задержку и стоимость.
8. **Отказоустойчивость.** Проверить позитивный путь и как минимум два отрицательных: неизвестная capability/версия или агент; повтор без двойного эффекта; cancel/timeout; MCP tool вне scope или недоступен; некорректный ответ модели. Показать безопасный резервный сценарий и восстановление.
9. **Обоснование выбора и паспорт.** Обосновать необходимость LLM и отклонённый более простой вариант; оформить **паспорт архитектурного решения** (альтернативы, владельцы границ, доверительные домены, внешний эффект, границы полномочий, доказательства, условия пересмотра и отката).

## 4. Индивидуализация (примеры вариантов)

| № | Сценарий | Инструмент по MCP | Паттерн |
|:--:|---|---|---|
| 1 | Помощник по обработке заявок (маршрутизация) | доступ к БД/справочнику | планировщик–исполнитель |
| 2 | Ассистент анализа документов | файловый/поисковый инструмент | ReAct + критик |
| 3 | Помощник планирования задач | календарь/трекер | Plan-and-Solve |
| 4 | Модерация и проверка контента | внешний валидатор/правила | критик + human-in-the-loop |

Иные варианты — по согласованию с преподавателем при сохранении набора артефактов и наличии ответственного контура.

## 5. Требования к результату и формат сдачи

Обучающийся предъявляет: код и конфигурацию; таблицу границ A2A/MCP; Agent
Card/capability и task lifecycle; scope-bound grant без секрета; трассы с
раздельными message/artifact и журнал вызовов инструментов; позитивные,
негативные и recovery-тесты; паспорт архитектурного решения; краткую инструкцию
запуска; обоснование выбора LLM. **Формат сдачи:** коммит(ы) в учебный
репозиторий + устная защита.

## 6. Живая защита и правила использования ИИ и внешних ресурсов

- Защита **устная**: обучающийся воспроизводит сквозной сценарий и **на месте вводит нарушенный режим** (отключает инструмент/имитирует некорректный ответ), демонстрируя переход к резервному сценарию и работу ответственного контура.
- Обучающийся объясняет, **где решение принимает человек или ответственная роль, а где LLM формирует проверяемое предложение**.
- Репозиторий — артефакт, но не достаточное доказательство самостоятельного понимания.
- Использование ИИ-ассистентов **при разработке** допускается с указанием промптов и критическим анализом; при этом LLM-компоненты самой системы описываются и ограничиваются явно.

## 7. Критерии и шкала оценивания

Оценивание — по [рубрике `rubric-01.md`](rubric-01.md). Работа засчитывается при
итоге не ниже **3 из 5** баллов и успешной живой защите. **Обязательное
условие:** значимое действие не выполняется LLM-компонентом без отдельного
полномочия и проверки/подтверждения; предусмотрены stop/revoke и резервный
сценарий. Упоминание A2A/MCP без соответствующего действия и negative test не
оценивается как реализация протокола.
